# Vue / Nuxt

本页补充 [TypeScript / JavaScript](typescript.md)，不另建一套相互冲突的基础规则。

## Vue 语法与类型覆盖

- ESLint 必须理解 Vue SFC，TS 脚本由对应的 TS parser 处理，不能把整个 `.vue` 当普通 TS 文本。
- Vue 语义规则与框架推荐配置可作为基线；属性换行、自闭合标签排版等交给 formatter，不通过重复排版规则制造冲突。
- 优先使用 Go 实现的 TS 检查后端及其 Vue 兼容层，但覆盖范围必须包含 `<script>`、`<script setup>`、模板表达式、props、emits 和跨组件类型。
- Vue 模板严格检查以 `strictTemplates: true` 为目标；框架生成类型和声明必须进入正确的项目范围。
- 普通 TS 文件通过原生编译器不代表 Vue 模板通过检查。编辑器诊断与 CLI 类型检查也不是同一入口。
- 原生方案不支持项目所需能力时，允许为该范围保留 Vue 官方兼容检查器；不得通过排除 `.vue`、关闭模板检查或把组件全声明为 any 来满足原生工具偏好。
- `vue-tsc`、`tsc` 等命令名本身不证明检查后端是否原生；具体依赖版本、兼容层和模板覆盖才是判断依据。

## Nuxt 路径别名

- 应用内部导入尽可能使用项目及 Nuxt 已有 alias，避免 `../../..` 和同一模块多种路径写法。
- `~` / `@` 通常指向应用 source directory，`~~` / `@@` 通常指向 root directory；实际含义以项目 Nuxt 配置为准，不能假定 root 与 source 相同。
- `#imports` 等框架虚拟模块按框架语义保留；`#shared`、`#server` 或其他别名只有在项目版本、配置和解析工具确实支持时才使用，不假定每个 Nuxt 版本都内置同一套别名。
- 静态 import/export、常量动态 import 和类型导入应遵循相同路径约定。带运行时计算的导入不能通过字符串检查冒充完整解析。
- 别名必须在构建器、类型检查和测试中指向一致位置；不以重复维护互相漂移的路径表替代框架生成配置。
- 客户端代码不得因为可以解析某个 alias，就导入服务端凭证、数据库适配器或其他 server-only 实现。
- 跨包引用优先包的公共导出，不以应用 alias 穿透另一个包的内部源码。

## 合法例外

- Nuxt 保留文件名、布局、页面路由以及 Vue 项目的约定组件名，可以例外于通用 kebab-case 规则；普通工具模块仍遵循该规则。
- 框架生成入口、包发布产物、独立于应用解析环境运行的脚本允许必要的相对路径，范围必须具体。
- CSS URL、HTML 资源路径不应直接套用 JS 模块导入规则。
- 不要求为了 alias 改写框架已正确处理的自动导入。

## 正反例

以下片段假设 `~/components` 已正确指向应用组件目录，文件内容未发生改变。

```ts
// 反例：同一应用内部依赖目录深度。
import StatusBadge from '../../../components/status-badge.vue'

// 正例：使用项目已存在的应用 alias。
import StatusBadge from '~/components/status-badge.vue'
```

两行是替代写法，不应同时出现在同一文件中。正例只证明路径约定；组件是否允许被该模块依赖，仍由模块边界决定。
