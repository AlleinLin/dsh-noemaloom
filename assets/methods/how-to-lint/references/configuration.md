# 环境配置集中化

环境配置属于系统与运行环境之间的边界，不是散落在业务代码里的全局变量。

## 读取与校验

- 环境变量只允许由明确的配置模块或配置入口读取。业务模块依赖解析后的配置对象或注入的配置值。
- 配置边界负责必填项、类型、范围与组合关系的运行时校验；错误应明确说明配置项与原因，不暴露秘密值。
- 默认值属于配置定义，不得由各个业务调用方自行拼接不同默认值。
- `as number`、`as string` 等类型断言不是运行时校验；数字、布尔值、URL 等必须实际解析。
- 配置优先级必须确定，不能在多个位置隐式覆盖同一项。
- 动态配置允许通过明确的 provider 读取和更新，不强制所有配置在模块导入时永久冻结。

## 适用边界与例外

| 场景 | 约束 |
| --- | --- |
| Node 服务 | `process.env` 由配置边界读取，包括别名和解构访问 |
| Vite 前端 | `import.meta.env` 由前端配置边界读取，仅暴露公开值 |
| Nuxt | 私有/公开 runtime config 分离，业务代码通过框架配置接口或应用配置适配层访问 |
| Python | `os.environ`、`os.getenv` 等读取集中在配置模块 |
| Go | `os.Getenv`、`os.LookupEnv` 等读取集中在配置包 |
| 构建、启动、测试脚本 | 可以是独立配置入口；不能因此放宽整个业务目录 |

使用原生配置框架时，配置入口可以是 settings 类、依赖注入 provider 或框架配置文件，不强制命名为 `config.ts`。配置包可以含多个内聚模块，不要求堆成一个巨型文件。

## 秘密与客户端

- 密码、令牌、私钥和服务端凭证不得出现在公开配置、客户端 bundle、错误消息或日志中。
- 前端公开环境变量前缀不提供保密能力。
- SSR 项目不能把包含私有字段的整个 runtime config 对象传给客户端。
- 测试可以注入配置或在限定的测试环境适配层模拟环境变量；不应为测试方便向生产业务代码增加直接环境读取。

## 正反例

以下为 TS 结构示例，省略具体校验库和业务实现。

反例：业务模块直接访问并重复解析环境变量。

```ts
const retryLimit = Number(process.env.RETRY_LIMIT ?? '3')
```

正例：配置边界定义、解析并校验 `retryLimit`；业务代码只使用该结果。

```ts
import { config } from '@/config'

const retryLimit = config.retryLimit
```

`@/config` 只是示例别名，不要求所有框架采用它。针对直接访问的 AST 检查不自动覆盖反射访问、别名和跨函数传递；规则不得声称已封锁其实现没有覆盖的路径。
