# 自定义规则的正反例与检测边界

每条自定义 lint 规则必须有正例和反例测试。这里规定检查器本身的质量，不规定测试执行流程。

## 规则定义

- 规则必须说明目标约束、受检语言/文件范围、报告位置、合法例外和已知检测边界。
- 正例必须通过，反例必须产生预期诊断；测试不应只断言任意错误存在。
- 例外必须有正例，同时有“类似但不满足例外”的反例，避免局部豁免变成绕过通道。
- ESLint 自定义规则优先使用 RuleTester 或对应语言的等价测试设施；Go analyzer 优先使用 `go/analysis/analysistest`。
- 不得仅凭 AST 子树、属性名或函数名就宣称具备完整控制流、跨文件符号解析或数据流分析能力。

## 必要的用例类别

| 主题 | 正例 | 反例 / 边界 |
| --- | --- | --- |
| 异常处理 | 保留原因的重抛、真实失败报告、特定预期错误降级 | 无绑定/空 catch、注释、void、未执行嵌套函数里的日志、无关同名处理函数 |
| 异步错误 | await、向上返回、有明确拒绝处理的后台任务 | 裸 Promise、仅 void、处理器自身产生无人处理的拒绝 |
| 环境读取 | 配置入口读取，业务代码使用解析结果 | 业务模块直接读、导入别名、解构、计算属性；实现不支持的形式应明确标注 |
| 路径别名 | 项目有效 alias、限定生成入口例外 | 深层相对 import、re-export、常量动态 import、类型导入、错误跨端依赖 |
| 作用域 | 真实目标符号及合法局部同名变量 | 仅同名而无关的对象/函数被误报，或目标对象通过别名绕过 |
| 文件范围 | 手写源文件进入检查，限定生成文件排除 | 忽略规则意外排除整个业务目录，或例外覆盖过宽 |

规则只对其声明支持的语法形式负责；尚不支持的检测形式不能伪装成已经覆盖。规范要求与检查器目前的覆盖缺口应明确区分。

## Parser 与类型服务

- 声称支持的 JS、TS、TSX、Vue 形式必须有相应 parser 下的测试，而不是用同一段 JS 解析结果代替全部语言。
- 依赖类型信息的规则必须有实际类型服务的测试；没有类型服务时的行为必须明确，不能静默当作检查通过。
- Vue/Nuxt 类型检查的测试应含故意错误的模板表达式、props/emits 和跨组件类型，防止只检查到普通 TS 文件。
- 配置类测试应覆盖真实 alias 解析和受检文件选择，不仅检查配置对象能够被导入。

## 自动修复

- 自动修复不得改变运行语义、错误传播、公开协议、模块加载副作用或配置访问时机。
- 有 fixer 的规则必须验证修复后的代码、再次修复的幂等性，以及不应自动修复的歧义情况。
- 将 null 改成 undefined、改写异常处理、移动配置读取、重构函数边界通常涉及语义，不应仅凭语法命中就自动改写。
- formatter 的排版输出不代替自定义语义规则的测试。

本仓库的文档示例只解释规范；应用项目中的自定义规则实现仍须拥有自己的可执行测试。
